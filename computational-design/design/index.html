Iterative design Theory

How site, program, and concept drive every system — before geometry becomes a script.

Design starts as constraints, not form

Iterative design theory treats the project as a set of inputs that must stay legible through every revision. Site conditions, program requirements, and the governing concept are encoded as parameters and rules long before a façade or plan is finalized.

Computational models are not a shortcut around design thinking — they are where design thinking is recorded. Each iteration tests whether the concept still holds when code, regulation, and constructability push back.

Three inputs that drive every system

  • Site — topography, climate, access, views, and context boundaries become hard limits in the model.
  • Program — room sizes, adjacencies, circulation, and capacity are structured as editable data, not drawn exceptions.
  • Concept — the organizing idea (pavilion, pinwheel, closed loop) is written as a rule set that geometry must follow.

Code and regulation as design material

Building code, zoning envelopes, and green-design thresholds are not checked at the end — they are part of the design substrate. Setbacks, height limits, egress widths, and energy targets enter the model as constraints that shape what form is even possible.

Programming — whether in Grasshopper, Dynamo, or Python — is how those constraints stay coupled to geometry. Change the program table or the code assumption, and the model updates without redrawing from scratch.

Iteration with traceable decisions

Each design option is a branch, not a throwaway sketch. Parameters, assumptions, and outcomes are documented so the team can compare alternatives against the same site and program baseline.

That is the practical difference between generative novelty and iterative design: the model preserves intent across revisions, and every step remains explainable to a reviewer, client, or contractor.
